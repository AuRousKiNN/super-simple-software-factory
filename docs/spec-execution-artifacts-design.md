# SSSF 规格与执行工件统一设计

状态：已实施，确定性测试与真实 smoke 已通过。实施范围、验证证据和保留限制见 [实施验收记录](spec-execution-artifacts-validation.md)。
日期：2026-09-24。

## 1. 目标与范围

将 planner 的规格、decomposer 的拆解结果和 documenter 的执行说明聚合到同一个规格目录。用户通过一份 README 了解该规格目前落实到什么程度，再按需查看目标定义、ticket 和历史执行报告。

三类文档分别承担：

- spec.md 记录目标：应当实现什么，以及完成标准。
- 规格目录的 README.md 记录现状：已实现什么、验证到哪里、仍有哪些缺口和阻塞。
- executions/ 记录历史：每次执行做了什么，结论与证据是什么。

documenter 每次完成记录时，同时追加本次执行报告并更新累计现状。app_docs/ 停止作为新产出的根目录。

本次范围包含目录、身份与路径分配、文档职责、输入输出合同、状态依据、发布流程、权限和验证要求。运行调度、自动续跑和跨仓库状态管理不在本次范围内。

## 3. 目录与身份

### 3.1 标准结构

~~~text
specs/
  README.md
  login-rate-limit/
    README.md
    spec.md
    spec.tickets/
      ticket-set.md
      tickets/
        TICKET-LIMIT.md
        TICKET-INTEGRATION.md
      index.json
    executions/
      <adw_id>/
        <execution_id>.md
~~~

spec.tickets/ 仅在发生拆解时创建。executions/ 仅在实际发布记录时创建，不预建空目录或占位报告。

两级 README 的所有权不同：

| 工件 | 维护者 | 内容 |
|---|---|---|
| specs/README.md | runtime | 各规格的标题、入口、观测时间、状态摘要与历史入口 |
| specs/<spec_key>/README.md | documenter；runtime 管理事实元数据与导航 | 对该规格落实现状的语义总结 |
| spec.md | planner | 完整需求、公共契约、验收标准及 revision |
| spec.tickets/ | decomposer；runtime 生成 index.json | 当前拆解定义 |
| executions/<adw_id>/<execution_id>.md | documenter；runtime 发布 | 单次执行记录，发布后保留历史 |

### 3.2 稳定身份

spec_key 是规格目录的稳定标识，独立于 ADW session，由使用 SSSF skill 的启动 Agent 根据需求和仓库已有目录决定。优先使用可读名称，需要区分同名需求时由启动 Agent 选择明确后缀。标题可调整，目录在创建后保持稳定。

新规划入口要求启动 Agent 显式传入 spec_dir，例如 specs/login-rate-limit。启动 Agent 先确认这是新规格还是已有规格的继续工作，再选择目录；用户无需亲自命名。这里的启动 Agent 是使用 SSSF skill 的编排者，不新增 ADW 角色，也不增加一次专门命名的 Agent 调用。

runtime 校验 spec_dir 为 specs/ 下符合布局的仓库相对目录，检查越界、符号链接和冲突，并按原样创建、持久化绑定，将 spec_path 派生为 <spec_dir>/spec.md。runtime 不从需求提炼名称，也不提供 task-<id> 默认值或自动改名。新建时目录已被占用则明确报错，由启动 Agent 判断继续已有规格还是另选目录；恢复同一已绑定 session 时沿用原绑定。

规划入口的目标参数分为两种互斥用途：新建使用 --spec-dir <目录>，修订已有规格使用 --spec <路径>。遗漏目标、同时提供两者或传入冲突绑定时，在派发 planner 前报错。参数名属于本设计的拟实施合同。

已有规格通过明确 spec_path 定位。修复、补证、重新审查和后续实现继续关联同一目录；规划内容变化时仍按现有合同更新原文件、递增 revision，并使用新的 session 重新绑定定义。

一个运行的执行记录只归属一个根规格。跨规格工作由 ADW 显式分成多个记录目标，不根据 diff、文件名或自然语言猜测归属。

### 3.3 执行记录身份

adw_id 用来聚合 session 内的记录。execution_id 由 runtime 在一次记录调用开始前分配并持久化，包含可读阶段名和唯一后缀。

不能仅用 phase 名称作为文件名：复用 session 再次启动脚本可能出现同名阶段。JSON 修复和 gate 重试沿用当前 execution_id；另一次独立记录调用分配新 ID。

相同发布请求重放时，已有相同内容视为成功；已有不同内容则显式报冲突。发现历史报告需要纠正时，追加说明并引用原报告，不覆盖原报告。

所有结构化路径采用仓库根相对 POSIX 路径。Markdown 内的导航链接按正式发布位置计算，确保提交到仓库后可以浏览。

## 4. README：规格落实现状

### 4.1 内容与阅读目标

README 应使读者快速回答：

1. 这项需求现在具备哪些能力？
2. 哪些结论已有验证，哪些仍待确认？
3. 哪些缺口或阻塞影响继续推进？
4. 下一次执行应接着处理什么？
5. 这些判断针对哪个规格版本、哪份代码及哪些证据？

推荐正文包含现状摘要、需求落实表、当前阻塞、下一步和执行报告导航。具体标题和排版允许按任务规模调整，不设置 Markdown 标题或表格格式门禁。

需求落实表可采用以下表达：

| 需求 | 实现情况 | 验证情况 | 依据与限制 |
|---|---|---|---|
| REQ-LIMIT | 已实现请求计数和拒绝逻辑 | 自动检查通过 | 引用执行报告及适用代码基线 |
| AC-RESTART | 尚待确认 | 重启场景未验证 | 需真实环境验证 |
| REQ-CONFIG | 未实现 | 未执行 | 后续 ticket 负责 |

实现情况和验证情况分别表达，避免把“代码已写完”显示为“已验收”。阻塞可与部分完成同时存在，不用单个枚举吞掉这些信息。

### 4.2 累计更新

documenter 必须读取已有 README 和必要的历史报告，以本次目标、差异及证据更新受影响的结论。执行一个 ticket 时，保留其他需求的已知状态及其适用范围。

历史结论不会因为出现在上一份 README 中就自动获得当前有效性。只有证据仍适用或已完成复核，才能继续表述为当前已验证；否则保留原观察结果并标记待复核。

新规格由 runtime 生成最小入口，说明尚未形成执行观察，不能在初始化时宣称功能不存在。planner 可发现已有能力，但正式落实现状由后续 documenter 根据证据整理。

### 4.3 观测基线与受管事实

README 是最近一次明确观测的结果。每次发布至少记录：

- 所属 spec_path、规格 revision 与内容哈希。
- 观测时的代码 commit；存在未提交实现时，补充内容快照标识。
- 更新时间、最新执行报告、观察范围为整个 spec 或指定 ticket。
- 最近一次有依据的验收范围、结果及来源；没有时明确为尚未确认。
- 该观察是否已知需要复核，以及具体原因。

这些字段由 runtime 根据绑定与实际证据写入受管 frontmatter，并将基线、验收范围和失效提示渲染为页面顶部的可见事实区。documenter 维护语义正文，不能通过声明元数据签发验收。

正文的“已验收”必须与受管事实一致；可以陈述“实现已完成、必要人工验证尚未执行”等更细的语义判断。

代码基线以被检查、审查的实现为准，不以之后仅提交执行文档的 commit 冒充验证对象。快照排除本次生成的 README、执行报告和索引，避免自引用；不能笼统排除可能影响功能的配置、测试等输入。

## 5. 执行报告

每份报告记录一个明确范围内的执行观察：

- 执行目标：根规格及其版本、实施或复核范围、相关 ticket 和需求。
- 实际工作：实现、修复、检查或补证，以及实际改变的文件。
- 目标落实：本次完成项、发现的偏差及其影响。
- 验证与验收：实际执行的检查、审查结论、人工证据、适用基线和未完成义务。
- 阻塞与遗留：问题归属、解除条件和继续所需输入。
- 后续衔接：下一次执行可直接使用的上下文与证据入口。

允许记录未验收、环境受阻、人工验证待办和仅补证的执行。报告生成成功只表示记录工作完成。

runtime 为报告附加身份、目标、代码基线、时间、来源引用及哈希。正文保留理解结论所需的关键信息，详细日志可链接到现有审计工件；日志缺失时必须说明，不能将历史摘要当成可重新签发验收的原始证据。

报告在发布时记录已经发生的事实。尚未完成的 Git 提交、run.finish() 或验收记录签发必须明确为待完成，不能预写“本次运行最终成功”。需要记录后续结论时，由宿主更新现状中的受管事实，或通过新的记录调用追加报告。

## 6. 状态、证据与验收所有权

### 6.1 不混淆三类结果

| 结果 | 决定者 | 含义 |
|---|---|---|
| 文档调用成功 | documenter 输出合同与发布校验 | 两份文稿完成，且正式发布成功 |
| ADW 运行接受 | run.finish() | 本条工作流的阶段与接受条件满足 |
| 规格或 ticket 验收通过 | 明确承担该范围验收的 ADW 及其宿主记录 | 该目标的实施、检查、审查、必要人工验证和适用性义务满足 |

规划 ADW 成功、文档阶段成功、builder 调用成功或单个 ticket 验收，均不能自动升级为完整规格验收。

完整规格显示已验收，必须绑定当前定义、适用代码基线和整个规格的集成结论。现有 ticket-acceptance.json 继续作为 ticket 依赖证据，README 和执行报告不替代它。

需要展示完整规格验收时，由负责整体实施与集成验收的 ADW 显式保存相应宿主回执。回执至少标识目标、定义哈希、基线、检查与审查证据和实际接受结果；文档模块只消费回执，不增加独立的验收算法。

### 6.2 新证据与旧结论

- 新增 diff：可更新实现情况；验证结果取决于适用于该实现的证据。
- diff 为空但完成新检查或人工验证：允许更新验证现状并追加报告。
- 无代码变化但出现或解除阻塞：允许记录状态变化和来源。
- 没有任何新的事实、证据或记录请求：返回无变化，不创建重复报告或空提交。
- 规格或 ticket 定义改变：保留历史报告，将受影响结论标记为待复核；不能把旧定义的通过结果移植到新定义。
- 明确取消某项需求：先由 planner 修订 spec，documenter 再解释现状变化。

第一版保守识别 freshness：定义哈希不同，或实现快照与证据适用范围不能确认一致时，标记待复核。自动判断无关代码改动不影响证据不在本次范围内。

### 6.3 静态文件的更新边界

runtime 在规划发布、执行记录发布、验收结果落盘及显式重建索引时检查可确定的失效条件。不能在无人运行工作流时保证仓库中的 Markdown 自动反映后来所有代码变化。

因此页面始终显示“截至何时、基于何版本”的观察信息。已知失效时，宿主先更新受管提示和索引，再由下一次 documenter 调用重整正文。旧正文可以保留历史价值，但页面必须明确提示其适用限制。

## 7. 输入输出合同与发布

### 7.1 DocumentContext

新增具体的执行记录输入类型，由 code 阶段构建并通过 AgentCall 的明确字段传入，不继续仅靠 previous 或 notes_for_next_agent 拼接上下文。

最小输入包括：

| 字段组 | 内容 |
|---|---|
| 归属 | 根 spec 引用、spec_key、SpecWorkItem 或 TicketWorkItem |
| 当前观察 | 已有 README 引用与摘要基线、必要历史执行报告 |
| 实际变化 | 可选 ChangesOutput、实际基线、变更文件与 diff 引用 |
| 执行证据 | 实际检查结果、ReviewOutput/路由回执、人工验证与验收引用 |
| 本次范围 | 实施、修复、补证或阻塞记录，以及明确的覆盖目标 |
| 发布绑定 | execution_id、两个暂存路径、正式目标路径、预期旧 README 哈希 |

代码负责聚合事实，documenter 负责解释事实。正文可以引用理解现状所必需的已有代码文件；“本次变更文件”仍必须来自实际变化捕获。原先禁止引用未修改文件的规则需要据此收窄。

输入引用缺失或哈希不匹配时显式报错；可选证据未提供时明确标记未验证，不用 Agent 猜测填充。

### 7.2 文稿与正式输出

建议新增 DocumentDraftOutput，作为 documenter 的具体输出类型，保留 status、summary、artifacts、commit_message 和交接说明，声明：

- execution_draft_path：本次执行报告正文。
- overview_draft_path：更新后的规格 README 正文。
- documented_files：本次实际变化中被解释的文件。

两份文稿写入当前 invocation 的 reports/ 暂存区。artifacts 只列已经存在的暂存文件，不把尚未发布的目标路径当作已生成工件。

宿主发布成功后构建正式 DocumentOutput，包含 spec_path、document_path、overview_path、正式 artifacts 以及原文档提交说明。正式输出保留 document_path 表示本次执行报告，并新增 overview_path 表示累计现状。

两个类型、提示词 JSON 示例、AgentCall.output_type 和消费方同步调整。Python 类型负责结构合同，语义质量由角色判断及必要审查保障。

### 7.3 发布步骤

1. runtime 绑定目标、输入哈希、旧 README 哈希与唯一 execution_id。
2. documenter 完成两份正文；JSON/gate 修复沿用当前调用。
3. code 核查暂存文件存在且非空、目标未漂移、证据引用有效。
4. 发布前重新读取规格与旧 README，发现并发更新即中止本次发布，重新整理输入。
5. 宿主生成受管元数据和导航，发布不可覆盖的执行报告及更新后的 README。
6. 重建 specs/README.md，记录发布回执，向调用方返回正式 DocumentOutput。

沿用仓库现有写锁，并增加 README 哈希比较，防止用旧快照覆盖新进度。不同工作树产生的 Git 冲突应合并后重新核对现状，不能机械选择最后写入者。

多文件更新需使用暂存与发布记录保证可恢复。索引最后更新；出现中断时能区分未发布文稿、已发布报告和待同步现状，不能声称已经完成原子事务。正常恢复复用原 execution_id，不生成重复报告。

context_handoff/ 中仍可提供 document.md 和现状副本供后续阶段读取，由宿主从本次已发布版本复制。它们是交接副本，不承担正式规格目录的身份或历史索引。

## 8. 工作流接入与失败处理

### 8.1 新规格与拆解

使用 SSSF skill 的启动 Agent 在启动规划工作流前决定规格目录，通过 --spec-dir 显式传入。工作流的 code 阶段校验并创建该目录、保存绑定，将固定 spec_path 传给 planner；planner 继续维护自包含规格和 handoff 副本。

修订已有规格时，启动 Agent 明确选择已有 spec_path 并通过 --spec 传入。工作流内部的后续阶段继承同一绑定；由 ticket 启动的实施或复核从 ticket 解析根规格，不重新命名或创建规格目录。

规格发布后由 runtime 初始化入口、刷新总索引；既有规格修订时保留累计正文并标记旧观察需要复核。spec.tickets/ 继续通过当前派生方式定位。

planner 和 decomposer 的成功仅更新规划信息，不填写未经执行观察的功能完成状态。

### 8.2 实施、复核与执行记录阶段

包含 documenter 的 ADW 采用共同的“收集记录输入 → documenter → 发布”流程。完整 SDLC 在实现及证据明确后记录；遇到可控的业务阻塞，也可以记录当前成果与交接条件。

删除 adw_document.py 独立工作流，不提供仅调用 documenter 的替代工作流。执行记录作为实施、复核或恢复等所属业务 ADW 的阶段运行，由该 ADW 显式传入根规格或 ticket 目标及本次证据。缺少目标时在派发 documenter 前报错，不从最近修改的规格猜测归属。

直接请求 builder 的工作流可以继续存在；如果需要发布执行工件，调用方必须先关联一份规格。documenter 不创建或补写需求规格。

空 diff 不再单独作为禁止记录的条件。只要存在新检查、审查、人工证据或阻塞事实，就有可记录的执行增量。

本次不为每个没有 documenter 的 ADW 强制追加 Agent 调用。它们保留真实执行记录，并更新可机械确定的“现状尚未同步”提示；后续由包含 documenter 阶段的所属业务 ADW 在实施、复核或恢复时更新语义正文。只补证而没有代码变化的复核，也在该业务工作流中完成记录。

### 8.3 完成顺序与提交

documenter 和发布阶段通常在 run.finish() 前完成。此时只能写已完成的检查与审查结果，尚未签发的最终接受结果保持待确认。

run.finish() 记录实际结果后，宿主可将该结果投影到 README 的受管事实与总索引，并关联新签发的验收回执。此步骤只同步事实，不再启动 Agent，也不重复调用 run.finish()。

现有 finish 会释放工作区锁。待同步事项应在结束前持久化；结束后的事实投影重新取得同一工作区锁，并核对预期 README 与定义哈希。发现另一轮执行已更新内容时保留待同步记录，交给显式刷新合并，不能用旧快照覆盖新现状。

文档提交范围由具体 ADW 明确管理。现有完整 SDLC 可以保留 finish 前的文档提交；finish 后若受管事实发生变化，增加一次仅包含这些事实与索引的宿主提交。只提交实际变化的路径，不使用 commit_all 混入无关修改；本来不自动提交的业务 ADW 仍将结果留在工作区。

仅提交执行记录的后续 commit 不改变被验证的实现基线，也不为记录自己的提交而无限追加报告。受管字段不要求包含它自身所在 commit 的哈希。最终事实同步与对应提交都完成后，命令才报告用户工件交付成功。

若 finish 后事实投影失败，保留真实运行结果和失败详情，标记文档同步失败并支持显式重放。不能回写虚构验收，也不能宣称用户文档已完整同步；命令结果应明确暴露这项交付失败。

### 8.4 失败、取消和中断

| 情况 | 处理 |
|---|---|
| 检查失败、reviewer 明确阻塞，运行仍可正常控制 | 按 ADW 的既定阶段记录已知现状，最终保留未验收结果 |
| documenter 输出失败或发布校验失败 | 保留暂存证据与旧现状，标记本次记录未完成 |
| SDK 失败、权限违规、取消或信号中断 | 优先完成原有审计与权限恢复，不在 finally 中启动 documenter |
| 硬退出导致收尾来不及执行 | 下次显式记录或索引刷新检查未完成发布，提示现状可能滞后 |
| 实际执行状态不明 | 保持未知并要求恢复核对，不能解释为无变化或执行成功 |

已有 phase 异常路径会结束 session 并关闭 runtime，实施时必须尊重此生命周期。能够继续记录的业务失败应建模为结构化结果和显式分支；技术失败后，由后续业务 ADW 的 documenter 阶段整理已保存事实。已生成文稿的确定性发布恢复可直接重放宿主步骤，不需要独立文档工作流。

## 9. 总索引与执行历史导航

specs/README.md 由代码重建，内容来自各规格的受管元数据，不让 Agent 手工维护汇总列表。

至少展示标题、规格入口、最后观测时间、验收范围与结果、已知待复核/未同步提示。不要将 ticket 计数或最近一次运行颜色转换为整体完成率。

执行报告列表按 session 分组，规格 README 展示最近若干条及完整历史入口。

## 10. 权限与模块职责

新增共享模块，建议命名为 spec_artifacts.py，负责启动 Agent 所选规格目录的校验与创建、路径绑定、执行记录路径分配、元数据、文稿发布、幂等恢复和总索引。ADW 文件保留顺序、分支和验收决定。

SSSF skill 的启动操作约定同步更新：编排者负责选择新目录或已有规格，并把目标传给工作流。相关说明落到 cookbooks/run_adw.md 和 cookbooks/how_to_prompt_for_the_eng.md；模板及 make_adw 生成的规划入口使用同一目标参数合同。

角色写入边界：

- planner 只修改绑定的根规格和交接副本。
- decomposer 只修改当前 spec.tickets/ 的规划工件。
- documenter 只在当前调用的 reports/ 与允许的 handoff 范围写文稿。
- 正式 README、执行历史、发布回执和索引由宿主写入。
- builder 的内容权限继续沿用现有规则，并保护绑定定义及宿主工件，防止实施时修改记录来改变验收结论。

documenter 配置收敛到当前文稿暂存区，移除原有宽泛写入项。暂存方案必须走现有自动报告目录例外及终态权限核查，不能扩大为整个 data_dir 可写。

更新 permissions.py 的宿主工件保护及测试，确保 ignored 文件、失败、取消和异常路径同样受约束。

本文不要求修改 SQLite schema；运行关联与发布回执可保存在新增的宿主 session 工件中，并使用现有 trace 事件记录。用户可见工件自身保留足够的来源元数据，使总索引可从当前仓库重建。

## 11. 实施顺序与验收

### 11.1 实施顺序

1. 更新 SSSF skill 的启动约定与目标参数合同，实现所选规格目录的校验、创建和稳定绑定，以及受管元数据、发布回执与索引重建；保持现有 ticket 派生结构。
2. 扩展输入输出类型、documenter 提示词和文稿发布流程，落实 README 与历史报告双产出。
3. 删除 adw_document.py 独立工作流及其专属调用引用；将记录阶段接入完整 SDLC、复核、可控阻塞分支和 make_adw 生成链，同步 planner 接入、权限和生命周期处理。
4. 提供发布恢复工具，更新安装说明、操作参考、示例与项目指南。

### 11.2 验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 启动 Agent 选择新规格目录 | runtime 使用传入目录，所有阶段继承固定 spec_path，不自动命名或改名 |
| 新建目录冲突或未提供目标 | 在 planner 调用前明确报错，由启动 Agent 处理 |
| 继续已有规格或从 ticket 启动 | 复用所属规格目录，不创建新的规格目录 |
| 新建完整规格并实施 | 工件集中在一个目录，README 同时表达实现与验证现状 |
| 同一规格跨多个 session 推进 | 目录与 spec_path 稳定，执行历史分组清楚 |
| 同一 session 重复记录、同名阶段或重试 | 独立调用不碰撞，重放不重复发布 |
| 只完成一个 ticket | 累计现状更新该范围，完整规格不被自动验收 |
| 空 diff 下补证 | 可以更新验证结论，并保留新的证据来源 |
| 规格修订或基线变化 | 历史结论可查，当前页面提示适用限制或待复核 |
| 可控业务失败 | 展示已完成工作、阻塞原因和解除条件，不显示成功交付 |
| documenter/发布失败 | 原 README 不被不完整文稿覆盖，可恢复且不重复历史 |
| 取消、权限违规或硬中断 | 原有终态清理仍生效，后续能发现未同步状态 |
| 旧 README 在发布前被修改 | 发布报冲突，不能丢失其他进度 |
| 提交文档与最终验收 | 代码基线无自引用，最终事实与真实 run.finish 结果一致 |
| 独立文档工作流移除 | 分发模板不包含 adw_document.py，现有业务工作流仍可使用 documenter 阶段 |
| 业务工作流记录阶段未绑定规格 | 在 documenter 调用前失败，不猜测归属 |
| 越权修改其他规格或历史报告 | 权限核查发现并按现有机制恢复 |
| 重建总索引 | 从当前工件重建规格入口及执行历史导航 |

类型、提示词和调用点需要同步验证；模块变更运行完整确定性测试，并增加覆盖真实失败模式的发布、失效、权限及恢复测试。文稿的具体标题和段落布局不作为测试目标。

完成实现后，以一个小规格执行“规划 → 实施或 ticket → 记录 → 补证 → 再记录”的真实 smoke，检查用户能从 README 分清目标、现状和历史。若变更触及 visualizer 的事件或存储合同，再执行其构建检查。
